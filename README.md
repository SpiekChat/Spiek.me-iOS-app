Full native iOS version of **Spiek** — serverless chat where every message
is a Bitcoin SV transaction and your account is a key. Not a wrapper: the
entire UI is SwiftUI, and `SpiekCore` is a dependency-free Swift package
that reimplements the protocol, crypto, wallet and engine from scratch. No
WebView, no JavaScript, no third-party code.

On the protocol layer: `SpiekCore/Tests/SpiekCoreTests/Resources/vectors.json`
is **byte-identical to the Android app's copy** and was generated from the
web client's JavaScript. Transactions built here are byte-for-byte what the
other two clients build; the same twelve words open the same account on all
three.

## Requirements

- Xcode 16 or newer (the project uses filesystem-synchronized groups)
- macOS Sonoma 14.5 or newer
- iOS 17.0+ (iPhone; iPad rotates freely)
- Apple Developer account to run on a device — an **organization**
  enrollment is required for App Store submission (see below)

## Build & run

1. `git clone https://github.com/SpiekChat/Spiek.me-iOS-app.git` — somewhere local,
   not inside a synced folder (see [BUILD.md](BUILD.md) §2 for why).
2. Open `Spiek.xcodeproj` in Xcode.
3. Select the **Spiek** target → **Signing & Capabilities** → pick your
   **Team**.
4. Choose your iPhone or a simulator and hit **⌘R**.

> Bundle identifier: `me.spiek.app` — change it to something you own if
> `spiek.me` is not yours.

## Architecture

| Layer | Technology | Notes |
|---|---|---|
| UI | 100% native SwiftUI | onboarding, chats, conversation, wallet, You |
| Protocol core | `SpiekCore` Swift package, zero dependencies | SHA-256/512, RIPEMD-160, HMAC, AES-256-GCM, secp256k1, ECDSA (RFC 6979), BIP-39/32, BIP-143, the Spiek v2 envelope |
| Key storage | iOS Keychain, `WhenUnlockedThisDeviceOnly`; with the device lock on, `SecAccessControl` + user presence | no iCloud, no backup extraction; phrase and WIF reveal gated by Face ID |
| Storage | SQLite (replaces the web client's IndexedDB) | cached plaintext and cursors namespaced per account |
| Networking | URLSession — `spiek.me/api/v2`, WhatsOnChain, `sns.ordnet.io`, `search.ordnet.io` | 429 backoff, cancelled requests never shown as errors |
| Names | SNS (`name.web3`) and OpNS, verified not trusted | pinned resolver key, holder outpoint proved unspent, OpNS cross-checked on chain |

## Features

- **BIP-39 keys** — twelve words, `m/44'/236'/0'/0/0`; pre-BIP-39 phrases
  fall back to the legacy scheme automatically.
- **Chats** — one-to-one, groups and notes-to-self; `spiek:chat:…` codes
  also open the app directly.
- **Encryption** — direct messages encrypt as soon as the peer's key is
  known; peer key pinned only when it signed the record that announces it;
  per-chat lock; safety number.
- **Device lock** — Face ID / Touch ID / passcode guards the key, not just
  the screen.
- **Notifications** — local only, count only, never message text.
- **Money** — send sats inside a conversation (slide to confirm) or straight
  to an address, SNS name or OpNS name; wallet with balance, activity and a
  "messages covered" estimate.
- **Media** — images inscribed as 1Sat Ordinals in their own transaction,
  referenced by outpoint; size, quality and cost shown before broadcast.
- **Edits, reactions, withdrawals, replies, profiles** (name and bio on
  chain, picture stays on the phone), **block & report** (guideline 1.2).
- **Service fees** — 3 sats per text message, 10 per image, 10 per payment,
  to the operator address in `SpiekCore/Sources/SpiekCore/Wallet/ServiceFee.swift`.
  Protocol overhead is not charged. Identical schedule on Android and web.
- **Demo playground** — an in-memory chain to click through everything
  without spending anything.
- **Own-node mode** — all four endpoints configurable under *You*.

## Verification

The whole consensus-critical layer was rewritten in Swift. To prove it does
*bit for bit* what the reference does, vectors were generated by running the
original JavaScript in Node — addresses, WIF keys, deterministic signatures,
complete signed transactions, encrypted payloads — and are pinned in the
test target. The sharpest test, `testBuildMessageReproducesReferenceBytes`,
rebuilds two whole transactions from the private key up and demands an
identical hex string, signatures included.

## Security notes

- Keys live exclusively in the Keychain, this device only; with the device
  lock enabled the item sits behind `SecAccessControl` with user presence,
  migrated crash-safely via a scratch copy.
- A privacy shield covers the scene the moment it goes inactive, so the
  app-switcher snapshot never shows a conversation.
- Secrets on the clipboard are local-only and expire after a minute.
- Sign-out empties the store; a different phrase imported on the same phone
  inherits nothing.
- Randomness comes from `SystemRandomNumberGenerator`; AES-GCM tags are
  compared in constant time. Parts of AES and secp256k1 are *not*
  constant-time — see [SECURITY.md](SECURITY.md) for the documented
  limitations and the threat model.

## Tests

```bash
cd SpiekCore && swift test
# -> Executed 169 tests, with 0 failures
```

169 XCTests on the pure-Swift package: golden vectors (hashes, phrase keys,
WIF, addresses, pushData, signatures over SHA-256d, ECDH, AES-GCM, envelopes,
codecs, complete built transactions), BIP-39, SNS and OpNS acceptance
criteria, and engine scenarios (discovery, the `prev` chain, encryption
switching on, edits, reactions, withdrawals, media, groups, payments). Since
1.20 the suite also carries `GroupVectorTests` — the encrypted-group cipher
against `group_vectors.json`, ciphertexts produced by an independent
AES-256-GCM implementation and shared verbatim with the web and Android
suites, negatives included — and `FuzzTests`: thousands of deterministic
mutations (bit flips, truncation, lying length prefixes, corrupted
addresses, mutated group ciphertexts, malformed invite codes) against the
real decoders. CI runs the same command on every push. Native UI/Keychain
flows are covered by the on-device matrix in BUILD.md §12, not by XCTest
yet.
