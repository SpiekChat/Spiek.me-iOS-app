# Spiek for iOS — building and shipping

A fully native SwiftUI app. The protocol layer was ported from the Spiek web
client and is pinned to its byte-exact reference vectors. No WebView, no
JavaScript, no external dependencies.

---

## 1. What you need

| | |
|---|---|
| Xcode | 16.0 or newer (the project uses file-system synchronized groups) |
| macOS | Sonoma 14.5 or newer |
| iOS target | 17.0 |
| Developer account | **Organization** enrollment — see §7 |

There is nothing to download. No CocoaPods, no SPM fetch, no Node. Clone and
build.

---

## 2. Where to keep this project

**Not in Dropbox, iCloud Drive or Google Drive.** Put it somewhere local —
`~/Developer` is the conventional spot:

```bash
mkdir -p ~/Developer && cd ~/Developer && git clone https://github.com/SpiekChat/Spiek.me-iOS-app.git
```

This is not a preference. A sync client resolves a clash by leaving a *second*
copy of the file next to the original — `WalletView (conflicted copy).swift`,
or `WalletView 2.swift`. This target uses an Xcode 16 file-system-synchronized
group, which compiles **every** `.swift` it finds in the folder, so those copies
are compiled too. The build then fails with `Invalid redeclaration of
'WalletView'`, pointing at code that is perfectly correct. Xcode also writes to
its own project files constantly while it is open, which is exactly what
provokes the clash.

Keeping the `.zip` in a synced folder is fine. Working in one is not.

The **Check for sync conflict copies** build phase catches this and stops the
build with the file names and what to do about it, instead of leaving you with
a redeclaration error twelve files away from the cause.

## 3. Open and run

```bash
open ~/Developer/Spiek.me-iOS-app/Spiek.xcodeproj
```

Set your team in Xcode: select the **Spiek** target → **Signing &
Capabilities** → **Team**. The bundle id is `me.spiek.app`; change it to
something you own if `spiek.me` is not yours.

Then pick a simulator or your iPhone and hit ⌘R.

---

## 4. Run the test suite first

This is the most important step, and the reason the project is laid out the way
it is.

The entire consensus-critical layer — secp256k1, ECDSA, BIP-143 sighash,
transaction serialisation, the Spiek envelope, ECDH and AES-256-GCM — was
rewritten in Swift. To prove the port does *bit for bit* what the HTML version
does, reference vectors were generated by running the original JavaScript in
Node: addresses, WIF keys, deterministic signatures, complete signed
transactions and encrypted payloads.

Run them:

```bash
cd ~/Developer/Spiek.me-iOS-app/SpiekCore && swift test
```

The sharpest test is `testBuildMessageReproducesReferenceBytes`: it rebuilds two
complete transactions from the private key up and demands an identical hex
string, signatures included. Green means your iOS app writes exactly the same
records to the chain as the web version — and that a recovery phrase written
down in the browser opens the same account here.

If they pass, everything left is UI. If something fails, please open an issue
with the output (see CONTRIBUTING.md).

## 6. What differs from the HTML version

Deliberate deviations, all in the iOS version's favour:

**Key storage.** The web version keeps your private key in IndexedDB. The iOS
app puts it in the **Keychain** with
`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`: not in iCloud, not in your
device backup, this device only. That is what App Review expects of a wallet,
and it fits the promise that your recovery phrase is the only way back.

**Media transactions are funded.** The web version broadcast the image
transaction with no input and no signature. A real node rejects that. The iOS
version builds it through the wallet — funded and signed — with the data output
at index 0, so the reference stays compatible.

**No fork in the message chain.** Two messages sent in quick succession could
both point at the same predecessor in the web version. The engine now
serialises composing and tracks the last own txid separately.

**No browser alerts.** Every notice appears inline in the bar at the top,
errors included — there is not one `UIAlertController` in the app.

**Portrait on iPhone.** On iPad the app rotates freely.

### Carried over from the web client (v10)

- **Encryption is on by default.** A direct message encrypts as soon as the
  other side's public key has arrived. The lock in the conversation header is an
  opt-*out* per chat, stored on the channel, and it survives a restart.
- **Fee floor of 0.1 sat/byte.** Both the default and a hard minimum; anything
  lower stored by an earlier build is clamped on launch.

### Carried over from the web client (v13)

- **BIP-39 recovery phrases.** New accounts derive through the standard scheme:
  PBKDF2-HMAC-SHA512, 2048 rounds, then BIP-32 along `m/44'/236'/0'/0/0` (236 is
  the BSV coin type). A phrase from an older build has no valid BIP-39 checksum,
  so restore falls back to the legacy derivation automatically and says so. The
  scheme is stored per account and shown next to the phrase in **You**, and the
  restore sheet has a switch to force the legacy path.
- **Images are 1Sat Ordinals.** An image is inscribed as
  `<P2PKH> OP_FALSE OP_IF "ord" OP_1 <mime> OP_0 <bytes> OP_ENDIF` on a single
  satoshi, and that satoshi is inscribed **to the recipient**, so the picture
  lands in their wallet rather than yours. The old `"spiekmedia"` data output is
  still read, so images in existing chats keep working.
- **A composer before you pay.** Picking an image opens a sheet with size,
  quality and a "keep the original" switch, showing the byte count and the fee
  in sats before anything is broadcast. The 5 MB ceiling is enforced there.
- **Replies.** Long-press a message → Reply. The quote sits above the bubble and
  works for text, images, payments, withdrawn and unreadable messages alike. A
  quote whose message you do not have reads "in reply to".
- **Notes to self are encrypted too.** The notes channel stores the wallet's own
  public key, so the ECDH runs against yourself and produces a key only this
  wallet can derive. The lock in the header applies there as well, and can be
  switched off if you would rather keep plaintext notes. Notes written by an
  earlier build stay readable — they are plain records and are shown as such.
- **Safety numbers.** In an encrypted one-to-one, tapping the header opens the
  five-group fingerprint of both keys, to read aloud over another channel.
  Since 1.20 a group's header says which kind it is — *encrypted group ·
  everyone with the invite can read* (key in the invite) or *public group ·
  permanently stored on-chain* — instead of leaving the missing lock icon to
  imply anything.
- **Device lock.** *You → Security* can require Face ID, Touch ID **or the
  device passcode** — whichever the phone has — to open the app, and to reveal
  the recovery phrase or the WIF key. The lock comes up when the app leaves the
  foreground and on a cold start, and it covers the whole screen so nothing is
  readable in the app switcher. `NSFaceIDUsageDescription` is set; without it
  the whole feature fails on a Face ID phone.

  Since v17 the lock is a *keychain policy*, not only a screen: enabling it
  re-stores the account item under a `SecAccessControl` of
  `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` + `.userPresence`, so the
  keychain itself refuses to release the key without Face ID, Touch ID or the
  passcode. Disabling it migrates back to plain
  `AfterFirstUnlockThisDeviceOnly`. The migration is crash-safe (a scratch
  copy exists at every intermediate state, and reads fall back to it), a cold
  start with the lock on defers the keychain read until the lock screen's own
  prompt (whose `LAContext` is handed to the read — one prompt, not two), and
  once the app is unlocked the key lives in engine memory, so nothing else
  prompts during the session.
- **Notifications and a badge.** New messages found while the app is running
  raise a local notification and set the app badge; the announcement fires as
  the app is backgrounded — the last moment code runs. There is no push
  server and no background-refresh task, so nothing arrives while the app is
  suspended; this is deliberate. Permission is asked once, the first time the
  setting is switched on.
- **QR codes.** The receive screen and the chat code panel render a scannable
  code via CoreImage — no library.
- **Send to a bare address.** Wallet → Send now also takes a plain address, with
  no chat and no message record.
- **Onboarding quiz.** Before an account is created you are asked for three of
  your twelve words, so the phrase has actually been written down.
- **Wipe this device.** *You* can erase the Keychain entry and the local
  database. It says plainly that the phrase is the only way back.
- **Mirror broadcasts.** Optionally send each transaction to a second endpoint
  as well, so one node being down does not lose a message.

### Added on top of the web build

- **Chat name and picture, per device.** Anyone in a chat can set both — not
  only whoever created it — because neither is broadcast. The picture is
  centre-cropped to 250×250 and compressed until it fits under 20 KB, so a long
  chat list stays small. Long-press a chat, or use the pencil in its header.
- **Unsettled messages are pinned.** A message that has not reached a block
  sorts *after* everything that has, so it drops to the bottom of the
  conversation. It gets a bar at the top instead, from the moment the broadcast
  is accepted: tap it to jump to the message, or × to put it away until its
  state changes. There is no waiting period — an earlier build only pinned after
  two minutes *and* compared against `Date()`, which SwiftUI does not observe, so
  the bar often never appeared at all.
- **Your own profile.** Name, one-line bio and a picture under **You**. The name
  and bio are stored on this device the moment they are saved, and separately
  published to the chain on request; the picture never leaves the phone. Same
  size ceiling as a chat photo: 250×250, under 20 KB.
- **BSV price in dollars.** Fetched from WhatsOnChain
  (`/v1/bsv/main/exchangerate`) and refreshed every minute. There is no rate to
  type any more: `Settings.eurPerBSV` is gone, and screens show plain sats
  whenever no rate newer than 30 minutes is in hand, rather than a figure nobody
  checked.
- **The peer key is pinned.** An incoming `open` is only believed when the key
  it announces is the key that signed the record, and only when the chat does
  not already have a peer. Channel ids travel in the clear on chain, so without
  both, one transaction was enough for a stranger to take over a conversation
  and have this device encrypt to them. A refusal is shown in the chat rather
  than swallowed. `getTx` answers are bound to the txid that was requested, so
  nothing read out of them rests on the endpoint being honest.
- **One reaction per person per emoji.** Every reaction is its own transaction
  and nothing on chain marks one as a repeat, so they used to stack.
- **SNS and OpNS names.** The "open directly" field in **New chat** and the
  wallet's **Send** sheet both take a name; **Wallet → Names** and
  **You → Keys** both open the list of names this address holds. The answer is
  verified rather than trusted — see §8 and §9.
- **Service fees** *(since v16)*. Every user-initiated transaction carries one
  extra P2PKH output to the operator's address: **3 sats per text message,
  10 sats per image, 10 sats per payment** — whether the payment travels inside
  a chat or straight to an address. Protocol overhead (opening a chat,
  reactions, edits, withdrawals, profile publishes) is not charged. The
  address and the amounts live in one place,
  `SpiekCore/Sources/SpiekCore/Wallet/ServiceFee.swift`, and every call site
  reads them from there. Both payment sheets and the image composer show the
  fee before anything is broadcast.

v13's dark mode is deliberately **not** ported: the app stays light, which is
what `UIUserInterfaceStyle` in `Info.plist` pins.

## 7. App Store checklist

### 7.1 An organization account is required

App Review guideline **3.1.5(i)**:

> *Apps may facilitate virtual currency storage, provided they are offered by
> developers enrolled as an organization.*

Spiek stores keys and a balance, so this applies. An **individual** account gets
rejected: sign with an organization team (D-U-N-S-backed enrollment), not a
personal Apple ID.

### 7.2 Export compliance

`ITSAppUsesNonExemptEncryption` is set to **`true`** in `Config/Info.plist`, on
purpose. Spiek ships its own AES-256-GCM for end-to-end confidentiality. That is
*not* covered by Apple's exemptions — those only apply when encryption is
limited to authentication, signatures, DRM, or whatever the operating system
provides.

What that means for you:

1. Answer the encryption questions in App Store Connect. For a mass-market app
   using standard algorithms you land on the ENC exemption under
   EAR 740.17(b)(1).
2. Apply for an **ERN** (Encryption Registration Number) through the SNAP-R
   portal of the US Bureau of Industry and Security.
3. File an annual self-classification report with BIS and the NSA before
   1 February each year.

This is US export law, not an Apple formality; this document is not legal
advice — have it checked if you are unsure.

### 7.3 Privacy

`Spiek/PrivacyInfo.xcprivacy` is filled in: no tracking, and the two
required-reason APIs the app touches (file timestamps for SQLite's WAL, disk
space for the media cache) are declared. The manifest and the App Store
privacy label are different things: the manifest's empty collected-data
array does **not** make "Data Not Collected" correct. Messages, media and
profiles leave the device for the public chain, the wallet address goes to
the endpoints it watches (and to a BSV21 token index if configured), and
reports go by e-mail. Declare the label from the data map in SECURITY.md —
Apple requires in-app messaging under "Emails or Text Messages".

### 7.4 What reviewers will ask

Be ready for these — they are the predictable stumbling blocks:

- **How do I test this without money?** Put in the review notes that the
  onboarding has a demo playground ("or try the demo playground →") which runs
  entirely locally, with no network and no real value. Spell that step out in
  your test instructions, or the app comes back with "we were unable to review
  the functionality".
- **What happens to messages?** They sit permanently and publicly on the BSV
  blockchain. Say so in the app description and in your privacy policy; a
  reviewer who discovers this alone reacts worse than one who read it.
- **Can users harass each other?** Guideline 1.2 asks for a reporting
  mechanism and blocking. Since v17 both exist: any sender can be blocked
  (long-press a message → Block sender, or from the chat details sheet;
  managed under *You → Blocked*), which hides their records on that device
  and stops them counting toward badges. "Report a problem" — in the chat
  details sheet and under *You → Security* — opens a prefilled mail to
  hello@spiek.me carrying the channel id and recent transaction ids, never
  message text. Content on a public chain cannot be filtered server-side;
  say so in the review notes.

### 7.5 Archiving for TestFlight

Select **Any iOS Device (arm64)** at the top, then Product → Archive, and in the
Organizer choose **Distribute App** → **TestFlight & App Store**.

## 8. SNS names

Both namespaces are usable in two places, and **both are payments**:

- **Wallet → Send** takes an address, an SNS name or an OpNS name.
- **New chat → open directly** takes the same three, and binds a dust output to
  the resolved address.

Both use the same two-tap confirmation: the first tap resolves and shows what it
found, the second tap **resolves again** and acts only if the fresh answer
matches what was shown. A name sold between the two taps therefore cannot be
paid — that is what the freshness window and the outpoint check are for. The
panel is gated on the text currently in the field, so it can never describe an
address the field no longer names.

**You → Your names** lists what both indexes say this address holds. That list
is *not* a verification: `/reverse` returns bare strings and `/owner` returns the
index's own assertions, neither signed. The screen says so, and tapping a name
runs the real check. The two indexes are asked separately so one being down does
not hide the other, and the result panel derives its caption from what was
actually checked — a browsing lookup resolves at `verify` (SNS) and without the
payment requirements (OpNS), and the panel says exactly that rather than
borrowing the payment screen's wording. Read-only: no minting, no buying, no
listing for sale.
 `SpiekCore/Network/SNS.swift` is a port of the resolver's verification
rules; there is no third-party client and no private key is ever involved.

**What is checked.** The resolver signs its answer. The app recomputes the
sighash — `SHA256d("ORDNS-RESOLVE" 0x1f v 0x1f name 0x1f mailbox 0x1f …)` — and
verifies the DER signature against a public key pinned in the binary. The
freshness window (`expires`) is enforced. The address shown and used is derived
from the **signed** `holder_script`; the answer's own `holder_address` field is
not covered by the signature and is only used as a cross-check — if the two
disagree the lookup is refused.

**Key rotation.** A signer the app does not know is not accepted on the
resolver's say-so. `/pubkey` is fetched and the chain of rotation deeds is
walked from the current pin, each deed verified against the key it replaces. The
pin only moves for a chain that closes, and never backwards. The pin lives in
the Keychain, device-only.

**Two labels, never one.** A *domain* status (`not_verified` — the name exists
on chain but carries no ORDnet mark) and a *signature* status are different
things and are worded differently everywhere. `not_verified` is permanent until
the name is marked; `no_holder` is the temporary one.

**Look-alikes.** Invisible characters and mixed scripts are flagged as `high`
and there is no path past them — copy the address across instead. Digits that
read as letters are flagged as `low` and only informational.

**Assurance level: `prove`.** Signature, freshness window, *and* the holder's
outpoint proved unspent. The proof is a direct question about one outpoint —
`GET /tx/<txid>/<vout>/spent` on WhatsOnChain, where `200` means spent and `404`
means unspent. Deliberately not "is it in the holder address's unspent list":
that list truncates on a busy address and would report a good name as spent, and
it cannot answer at all for an outpoint whose script differs from the address the
name pays to, which is exactly the custody case.

`unknown` is a third answer and is never reported as spent — but it is not a
proof either, so at `prove` it refuses. OpNS takes the same position on the same
evidence; the two namespaces are not allowed to disagree about what an
unverifiable outpoint means.

**Extensions are not hardcoded.** They come from `GET /health` and are cached
for an hour. Retired extensions still resolve.

The tests in `SNSTests.swift` reproduce both spec test vectors byte for byte,
verify two real signed answers captured from the live resolver, tamper with each
of the eleven signed fields in turn, and exercise the rotation chain against
forged and gapped deeds.

## 9. OpNS names

A second, separate namespace: bare names with **no dot**, mined with proof of
work on 1Sat Ordinals under tree 0
(`58b7558e…9ccb25_0`, block 806214). `SpiekCore/Network/OpNS.swift` holds what
the protocol fixes; `OpNSTests.swift` covers it.

**The two namespaces never overlap.** A dot means SNS, no dot means OpNS, and
the check is in the core rather than in a view so a payment cannot be sent to
the wrong service. One trap worth knowing: Base58 is a subset of the OpNS
character set, so a lowercased address reads as a perfectly valid bare name —
only the checksum separates them, and `looksLikeOpNS` refuses anything that
passes `Address.isValid`.

**A near miss is a different name.** The index answers a name that does not
exist with the closest one it does have, flagged `fallback`. That is refused
outright, with both names shown. Because names are mined per letter, `alexander`
implies that `a`, `al`, `ale`… also exist as separate names with possibly
different owners — so the exact resolved name is always shown next to the
address.

**Ownership is the outpoint.** `OutpointProver` fetches the holder address's
unspent set and checks the outpoint the index named is in it. Three answers, not
two: `unspent`, `spent`, and `unknown` — and `unknown` never counts as `spent`,
because a lagging indexer must not condemn a good name. Paying requires
`unspent`.

**Paymail forms are shown, never paid.** Any host can serve any name and the
on-chain binding dies when the name is sold, so `naam@host` is recognised and
named but is never resolved into somewhere to send money.

**No mint or buy flows.** Showing, resolving and transferring only — that
decision has not been taken.

**The chain outranks the index.** The index says who holds a name; the raw
transaction decides. The locking script of the current outpoint is read back and
the address derived from it must equal what the index claimed — a disagreement
refuses the lookup rather than picking a side.

Same two places, same two-tap confirmation as SNS.

### Endpoints

    GET /api/opns/names?q=<name>     search, defaults to match=exact
    GET /api/opns/name/<name>        one name
    GET /api/opns/owner/<address>    every name held by an address
    GET /api/opns/status             the root, counts, last lineage run

Envelope `{ ok, fallback?, match?, results: [...] }`; a record carries `name`,
`owner_address`, `current_txid`, `current_vout`, `origin_txid`, `origin_vout`,
`ambiguous` and `lineage_verified`. A record without `current_vout` is dropped rather than
assumed to be output 0 — "the index did not say" and "output 0" are different
facts, and guessing would point both the holder recompute and the spent check at
the wrong outpoint.

**`lineage_verified` is enforced, fail-closed.** It certifies that the name
traces back through an unbroken chain of valid mints to the root of the tree —
i.e. that this is the canonical name rather than something that merely spells the
same. It says nothing about who holds it now; that is `current_*` plus the spent
check. Without the certificate a payment is refused. The worst that costs is a
false negative on a freshly mined name whose lineage pass has not run yet, which
reads as "try again later" — never a payment to the wrong party. It is
deliberately treated as temporary and never cached: the indexer runs
periodically and `false` can become `true`.

**`origin_txid`/`origin_vout` is the mint transaction of *that name*.** Every
record carries a different one and none of them is the root — it is identity and
traceability, not lineage. The root is a separate constant, pinned in the binary
and cross-checked once per launch against `GET /api/opns/status`. The pin stays
the pin: a disagreement refuses rather than adopts, and an index that does not
say which root it serves has confirmed nothing, so silence is refused too.

### Reading the index's answers

Every wire struct in `OpNSIndex.swift` has a hand-written decoder, and that is
not tidiness — it is a bug that cost every OpNS lookup in the app.

`/status` returns `"last_run": "2026-08-04 08:02:20"`, a *string*. It was
declared as an `Int`, and `decodeIfPresent(Int.self, …)` **throws** when the key
is present with the wrong type — it does not return nil. Swift's synthesised
decoder fails the whole envelope on one bad field, so a cosmetic timestamp made
`status()` throw `directoryUnavailable("unreadable answer")`. Because the root
check gates every lookup, *every* OpNS name failed with that message while SNS,
which has no such pre-flight, kept working.

The rules that came out of it:

- Only fields a payment cannot proceed without may fail a decode: the root on
  `/status`, and `name` + `owner_address` + `current_txid` on a record.
  Everything else is read leniently and defaults to the cautious value.
- Numbers and booleans are accepted in whatever JSON shape they arrive in. The
  index is SQL-backed, and such backends write `0`/`1` for booleans and quote
  numbers as strings.
- One unusable record does not fail the list — it is skipped. But a list where
  *nothing* survived is reported as an unreadable answer, never as "that name
  does not exist", which is a claim about the chain.
- The root check fails closed on what the index *said* and fails open on not
  being able to ask. A different root is permanent; a withheld root refuses too,
  but is re-checked every five minutes, so one malformed answer cannot lock the
  feature out until the app is force-quit.

## 10. Endpoints

By default the app talks to `https://spiek.me/api/v2/…`, like the web version,
with WhatsOnChain as the UTXO provider and as a second broadcast route.

Pick **Own node** during onboarding and an *Endpoints* block appears under
*You*, where you can set all four URLs. The `{txid}`, `{address}` and `{since}`
placeholders are filled in for you. Saving restarts the engine immediately — no
need to relaunch.

## 11. Changing things

- **Colours** — `Spiek/Design/Theme.swift`, `enum Palette`. One place; the whole
  app follows.
- **Copy** — currently inline English. For more languages a String Catalog
  (`Localizable.xcstrings`) is the next step; `SWIFT_EMIT_LOC_STRINGS` is
  already on.
- **App icon** — `Spiek/Assets.xcassets/AppIcon.appiconset`, 1024×1024 with
  separate dark and tinted variants.
- **Service fees** — `SpiekCore/Sources/SpiekCore/Wallet/ServiceFee.swift`.
  The operator address and the three amounts (message, image, payment) are
  constants there; nothing else needs to change to adjust them.
- **Protocol** — `SpiekCore/Sources/SpiekCore/Protocol/`. Change anything here
  and the app stops being compatible with the web version; the test vectors will
  tell you immediately.

## 12. Version history

Marketing version and build number track the release number: this build
ships as **1.20.1 (build 21)** — see [CHANGELOG.md](CHANGELOG.md) for 1.20.0
(encrypted groups, BSV21 balances, fuzzing) and 1.20.1 (keyed invites as
secrets, documentation corrections). The notes below are the v17 review
round, kept for history.

### v17 — 1.17.0

Pre-release review fixes, wallet correctness first:

- **Address version byte enforced.** `Address.hash160(from:)` now requires
  the mainnet P2PKH version byte. A BTC P2SH "3…", a Litecoin "L…" or a
  testnet address — all valid Base58Check with 20-byte payloads — used to be
  accepted and paid as mainnet P2PKH, burning the coins.
- **Fee-aware coin selection.** Inputs are selected until they cover the
  amount *plus the real fee of the transaction they produce*. The old
  fixed-guess selection failed a wallet full of small coins even when it held
  plenty, and reported the selected subtotal as "your balance". The fee model
  also counts the real varint length of large output scripts.
- **Amount cap.** Nothing may move more than the coin supply; a twenty-digit
  amount used to overflow UInt64 arithmetic and crash.
- **Malformed UTXO entries are skipped**, not fatal — a negative output index
  from an endpoint used to trap and crash every sync.
- **Sign-out empties the store.** A different phrase imported on the same
  phone no longer inherits the previous account's chats or cached plaintext;

### v16 — 1.16.0

- **Service fees.** One extra P2PKH output per user-initiated transaction, to
  the operator address hardcoded in `ServiceFee.swift`: 3 sats per text
  message, 10 sats per image, 10 sats per payment (in-chat or to a bare
  address). Protocol overhead — opens, reactions, edits, withdrawals, profile
  publishes — is not charged. Both send sheets and the image composer state
  the fee before anything is broadcast, and the payment sheet counts it into
  its affordability check.
- **429s are retried, then reported readably.** The sync fires a burst — one
  watch call per followed address, a `getTx` per new transaction, plus the
  UTXO fetch — and the endpoint's nginx rate-limits bursts. The REST adapter
  now backs off and retries twice (1.2 s, then 2.5 s) on a 429 before giving
  up. When an HTTP error does surface, the notice bar shows one readable line
  ("The server is busy right now — trying again shortly.") instead of a raw
  nginx HTML page.
- **Cancelled requests no longer show as errors.** Leaving the app while a
  refresh was in flight made iOS cut the connection, and the bare word
  "cancelled" then appeared as an error bar over the chat list.
  Cancellations are now filtered out of `report(_:)`; nothing is lost — the
  next poll picks everything up.
- Version set to 1.16.0, build 16 (was 1.0, build 1).

### v15

- **Every scrolling sheet has a close button.** Sheets are dismissed by
  dragging them down, which broke wherever something else claimed that drag.
  `SheetHeader` gained an `onClose` and all scrolling sheets pass it.
- **Wallet → Names reloads with a button, not pull-to-refresh.**
  `.refreshable` claimed the downward drag at the top of the list — the same
  gesture that dismisses the sheet — so the screen had become a trap: every
  attempt to swipe it away reloaded the list instead.

### v14

- **The peer key is pinned.** An incoming `open` is only believed when the key
  it announces is the key that signed the record, and only when the chat does
  not already have a peer — without both, one transaction was enough for a
  stranger to take over a conversation. A refusal is shown in the chat rather
  than swallowed, and `getTx` answers are bound to the txid that was
  requested.
- **One reaction per person per emoji.** Every reaction is its own
  transaction and nothing on chain marks one as a repeat, so they used to
  stack.
